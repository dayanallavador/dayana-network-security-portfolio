FORTIGATESD-WANIPSECLAB

FortiGate Dual-ISP SD-WAN Lab

A two-site lab built to understand how FortiGate makes path-selection decisions, detects WAN degradation and keeps site-to-site connectivity alive when an ISP fails.

IN THIS LAB 01 · Goal02 · Design03 · Failure 04 · Troubleshooting05 · Result06 · What I learned

01. Goal

The goal was not simply to make two tunnels come up. I wanted to reproduce the decisions a firewall has to make when two WAN links are available and one of them becomes unusable even though the physical interface remains up.

  • Build two sites with independent LAN subnets.
  • Provide two WAN paths.
  • Create IPsec connectivity between the sites.
  • Use Performance SLA checks to evaluate path health.
  • Force a degraded-link scenario and observe failover.

02. Design

Both FortiGates use SD-WAN members for the WAN interfaces. Health checks continuously test reachability and quality. SD-WAN rules then decide which member should carry traffic according to the configured strategy.

Key idea

An interface being up does not mean that the path behind it is healthy. SD-WAN needs an active measurement mechanism if we want it to react to upstream failures or poor quality.

03. Failure scenario

I deliberately broke the preferred path while keeping the WAN interface operational. This is more useful than simply shutting the port because it represents failures such as upstream packet loss or an ISP routing problem.

04. Troubleshooting

I checked the problem from the forwarding decision outward instead of changing configuration at random:

Policy→Route / SD-WAN→Health check
IPsec→Session→Packet flow
$ diagnose sys sdwan health-check $ diagnose sys sdwan service $ get router info routing-table all $ diagnose vpn tunnel list $ diagnose debug flow

The important part was correlating the SD-WAN health state with the route and the actual firewall session. A healthy tunnel alone does not prove that the expected traffic is using it.

05. Result

When the preferred path failed the SLA criteria, traffic moved to the surviving member and inter-site connectivity remained available. When the preferred path recovered and again met the configured thresholds, the topology returned to its intended state.

06. What I learned

The biggest lesson was to separate interface state, path health, routing decision and IPsec state. They are related, but they are not the same signal. Troubleshooting becomes much faster when each layer is verified independently.

TECHNICAL NOTEFORTIGATESD-WAN

How FortiGate SD-WAN chooses a route

A short mental model for separating routing, SD-WAN rules and Performance SLA checks when troubleshooting FortiGate path selection.

8 Sep 2026Reading time: ~4 minTopic: Routing / SD-WAN
CONTENTS01 · Mental model02 · SLA03 · Example04 · What to check

01. The mental model

When traffic does not use the WAN link you expected, avoid treating “SD-WAN” as one black box. Think of the decision as several checks that must agree.

Destination→Routing→SD-WAN rule
Member health→Strategy→Selected path

The routing table still matters. SD-WAN does not magically remove routing from the forwarding process; it adds policy and path intelligence around eligible members.

02. What Performance SLA changes

A Performance SLA can measure whether a member is reachable and whether metrics such as latency, jitter or packet loss meet the thresholds you define. This allows FortiGate to avoid a link that is electrically up but operationally poor.

Useful troubleshooting question

“Is the interface up?” is only the first question. The better next question is: “Does FortiGate consider this SD-WAN member healthy for this service?”

03. Simple example

WAN1

Interface: UP
Latency: 18 ms
Loss: 0%
SLA: PASS

WAN2

Interface: UP
Latency: 160 ms
Loss: 12%
SLA: FAIL

Both interfaces are technically up, but if the SD-WAN rule requires the SLA and WAN2 fails it, WAN1 can remain the valid path. This is why looking only at interface status can send troubleshooting in the wrong direction.

04. What I check first

$ diagnose sys sdwan health-check $ diagnose sys sdwan service $ get router info routing-table details <destination> $ diagnose sys session filter dst <destination> $ diagnose sys session list

My order is: confirm the destination and route, identify the matching SD-WAN rule, inspect member health, and finally verify the session/packet flow. That gives a much cleaner explanation of why FortiGate selected a particular path.

IPsec tunnel is UP, but traffic does not pass

A structured investigation of a tunnel that looks healthy from the VPN status but still fails to carry LAN-to-LAN traffic.

SymptomPhase 1/2 UP, traffic DOWN
Root causePolicy / NAT mismatch in the lab scenario
ResultBidirectional traffic restored
WORKFLOW01 · Symptoms02 · Hypotheses03 · Checks04 · Root cause05 · Fix06 · Verification

01. Symptoms

The VPN reports an established tunnel, but hosts behind Site A cannot communicate with hosts behind Site B.

02. Hypotheses

Instead of rebuilding the tunnel, I separate the possible causes: route selection, firewall policy, NAT, Phase 2 selectors and return-path behavior.

03. Checks

$ diagnose vpn tunnel list $ get router info routing-table all $ diagnose debug flow $ diagnose sys session list $ show firewall policy

04. Root cause

In this lab scenario, the traffic matched an incorrect policy/NAT behavior. The tunnel itself was not the failure.

05. Fix

Correct the matching firewall policy and NAT behavior so that the intended LAN-to-LAN traffic is forwarded into the VPN.

06. Verification

Repeat the original test and confirm bidirectional packet counters, session state and end-to-end connectivity.

Lesson

“Tunnel UP” proves the VPN control state, not the complete forwarding path.

BGP neighbor remains in Active

A routing case focused on proving basic reachability and session prerequisites before investigating route policy.

SymptomNeighbor stays Active
Root causeNeighbor/reachability mismatch in the lab
ResultAdjacency reaches Established
WORKFLOW01 · Symptoms02 · Hypotheses03 · Checks04 · Root cause05 · Fix06 · Verification

01. Symptoms

The configured BGP peer never reaches Established and no routes are exchanged.

02. Hypotheses

Check IP reachability, neighbor address, remote AS, update source and TCP connectivity before looking at route attributes.

03. Checks

$ show ip bgp summary $ show ip bgp neighbors $ show ip route $ ping <neighbor> $ show running-config | section router bgp

04. Root cause

The lab introduces a neighbor/reachability mismatch that prevents the TCP/BGP session from forming.

05. Fix

Correct the peer parameters or underlying reachability rather than changing unrelated BGP policy.

06. Verification

Confirm Established state, received/advertised prefixes and the resulting routing-table entries.

Both WAN members appear available, but a test session leaves through a different member than expected.

02. Hypotheses

Possible causes include route eligibility, rule matching, SLA state, configured strategy and an already-established session.

03. Checks

$ diagnose sys sdwan health-check $ diagnose sys sdwan service $ get router info routing-table details <destination> $ diagnose sys session filter dst <destination> $ diagnose sys session list

The lab demonstrates how rule/SLA state and session behavior can make the selected path differ from a simple “WAN1 is up” expectation.

Correct the SD-WAN selection logic where necessary and retest using a fresh session.

06. Verification

Validate member health, matching rule, selected path and the actual session egress interface.
