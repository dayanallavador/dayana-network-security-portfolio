TCP Server-RST: Firewall Accepts the Traffic, but the Connection Fails

Sometimes the firewall allows the traffic, but the TCP connection still fails. This note explains one simple case with server-rst.

17 Sep 2026Reading time: ~4 minTopic: TCP / Troubleshooting
CONTENTS 01 · Symptom 02 · What server-rst means 03 · Why ACCEPT appears 04 · Troubleshooting 05 · Root cause 06 · What I learned

Sometimes the firewall shows that the traffic is allowed, but the connection still does not work.

This can happen when a FortiGate session ends with server-rst.

At first, this can be confusing. The firewall says ACCEPT, so it looks like everything is correct. But ACCEPT only means that the firewall allows the traffic. It does not mean that the service on the server is working.

01. Symptom

The client tries to connect to a server using TCP, but the connection fails.

In the firewall log, we can see:

Action: ACCEPT Session end: server-rst

At the same time, the destination service shows:

TCP/53 NOT LISTENING

So the firewall allows the traffic, but the server does not accept the connection.

02. What does server-rst mean?

Normally, TCP starts a connection with three steps:

Client Server SYN --------> <-------- SYN/ACK ACK -------->

After this, the connection is established.

But in this case, the server sends a reset:

Client Server SYN --------> <-------- RST/ACK

This means that the server does not accept the TCP connection.

In FortiGate, server-rst means that the reset comes from the server side.

03. Why does the firewall show ACCEPT?

The firewall and the server check different things.

Match the policy→Allow traffic→Route packet
Send to server→Check service→Accept / reject

But the server can still reject the connection.

Key idea

Firewall ACCEPT does not mean that the service is working.

The network can be working, but the application can still have a problem.

04. Troubleshooting

First, I check the network path:

Firewall policy→Routing→NAT
Reachability→TCP connection→Listening port

If the traffic reaches the server, I check the TCP service.

In this case, the firewall was working correctly.

The problem was on the destination server.

05. Root cause

The destination service was not listening on TCP port 53.

Because the service was not listening, the server returned a TCP reset.

This matches these two results:

TCP/53 → NOT LISTENING server-rst

The firewall was not blocking the connection.

06. What I learned

Main lesson

Firewall ACCEPT does not mean Application working.

When I see server-rst, I check two things:

  • Can the traffic reach the server?
  • Is the server accepting the connection?

If the firewall allows the traffic and the server sends a reset, I should check the destination service, the port and the application.

This helps me find the problem faster and avoid changing firewall rules when the firewall is not the cause.
